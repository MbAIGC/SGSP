# SGSP P0 数据完整性 Bug：目录同步成功，但目录下的 `.sy` 笔记内容为空

## 问题现象

使用 SGSP 同步时，当同步范围选择“笔记文档”后：
- GitHub 中的笔记目录结构可以正常同步；
- 目标设备能够看到对应目录；
- 但是目录下同步过来的 `.sy` 笔记文件为空，文件大小为 0 bytes；
- 目录结构同步成功，但笔记实际内容没有同步过来。

例如源设备：

```text
notebook/
└── 2026/
    ├── A.sy        123 KB
    ├── B.sy        85 KB
    └── C.sy        210 KB
```

目标设备：

```text
notebook/
└── 2026/
    ├── A.sy        0 bytes
    ├── B.sy        0 bytes
    └── C.sy        0 bytes
```

## 严重级别

**P0 / 数据完整性问题**

这属于静默数据损坏风险。不能因为 GitHub API 返回成功或文件路径存在，就认为同步成功。

## 核心问题

需要检查当前流程是否把“目录/文件路径同步”和“文件实际内容同步”分成了两个没有严格绑定的流程。

可能出现：

```text
Directory → 成功
File Entry → 成功
Blob → 内容为空
```

或者文件路径已经创建，但实际 `.sy` 内容没有正确读取/写入。

## 必须检查完整数据链路

```text
同步范围选择
    ↓
笔记文档枚举
    ↓
本地 `.sy` 文件发现
    ↓
读取 `.sy` 文件内容
    ↓
生成 FileEntry
    ↓
生成 Blob
    ↓
生成 Git Tree
    ↓
创建 Commit
    ↓
Push GitHub
    ↓
目标设备 Pull
    ↓
读取 Git Blob
    ↓
写入本地 `.sy`
```

需要确认每一步传递的：

```text
path
content
size
hash
```

是否一致。

## 重点检查

### 1. `.sy` 是否真的被读取

确认“笔记文档”模式下是否真正读取 `*.sy` 内容，而不是只扫描目录和路径。

重点检查：

```text
isSyncable(path)
filterFiles()
getWorkArea()
buildSyncFiles()
```

以及所有负责枚举、读取、构造同步对象的函数。

### 2. 是否存在空字符串 fallback

重点搜索：

```js
content || ""
content ?? ""
catch { return ""; }
catch (e) { content = ""; }
new Blob([""])
```

任何：

```text
读取失败 → 空字符串 → 继续同步
```

都必须修复。

### 3. Blob 创建前验证内容

如果源文件：

```text
A.sy = 123456 bytes
```

生成 Blob 前必须确认实际读取到了内容。

最好记录：

```text
path
size
sha256
```

Blob 创建后必须与源内容匹配。

### 4. GitHub Tree 不能只验证 path

不能只验证：

```text
tree:
  notebook/2026/A.sy
```

存在。

还应验证：

```text
path
+
blob SHA
+
content size
```

文件路径存在不等于文件内容正确。

### 5. Pull 到目标设备同样验证

写入本地后至少验证：

```text
远端 Blob size
=
本地文件 size
```

更严格可验证：

```text
远端 SHA
=
本地 SHA
```

不一致必须判定同步失败。

## “只同步笔记文档”必须正确处理 `.sy`

当：

```text
同步范围 = 笔记文档
```

必须确保实际包含：

```text
notebook/**/*.sy
```

不能只同步目录结构。

重点检查同步范围过滤逻辑是否把 `.sy` 文件错误排除、错误映射或错误转换为空内容。

## 必须区分目录和笔记文件

目录只代表：

```text
path exists
```

`.sy` 文件代表：

```text
path
+
content
```

因此：

```text
目录存在
```

不能作为：

```text
笔记同步成功
```

的判断依据。

## 安全要求

必须增加强制不变量：

> **任何 `.sy` 文件在同步前后，如果源文件非空，则目标文件不得变成 0 bytes。**

如果源文件 123 KB，而目标文件 0 KB：

```text
同步失败
```

而不是同步成功。

## 禁止空内容覆盖已有内容

如果目标设备原来有正常内容：

```text
A.sy
size = 123 KB
```

同步过程中得到：

```text
A.sy
size = 0
```

**绝对不能覆盖本地文件。**

正确行为：

```text
检测到异常
    ↓
停止写入
    ↓
保留原 A.sy
    ↓
报告同步失败
```

## 验收测试

### Test 1：正常同步

源：

```text
A.sy = 100 KB
```

目标：

```text
A.sy = 100 KB
```

并且内容 Hash 一致。

### Test 2：多个目录

源：

```text
notebook/
├── A/
│   └── A.sy
├── B/
│   └── B.sy
└── C/
    └── C.sy
```

目标必须同时满足：

```text
目录结构正确
+
所有 `.sy` 文件存在
+
所有 `.sy` 文件非空
+
内容 Hash 正确
```

### Test 3：只同步“笔记文档”

开启：

```text
同步范围 = 笔记文档
```

验证所有 `*.sy` 必须包含实际内容，而不是只有目录。

### Test 4：模拟读取失败

故意让某个 `.sy` 文件读取失败。

预期：

```text
❌ 整次同步失败
❌ 不生成空 Blob
❌ 不创建包含空文件的 Commit
❌ 不更新 lastSyncCommit
❌ 不覆盖目标已有文件
```

### Test 5：远端 Blob 异常

如果 GitHub 返回的 `.sy` Blob 为 0 bytes，但同步状态认为该文件原本应该有内容：

```text
❌ 不覆盖本地正常文件
❌ 报告数据完整性异常
```

## 最终要求

同步成功的定义不能只是：

```text
GitHub API 返回 200
```

或者：

```text
文件路径存在
```

而应该是：

```text
目录结构正确
+
文件集合正确
+
文件内容正确
+
文件大小正确
+
必要时 Hash 一致
```

尤其对于 `.sy`：

> **“文件存在但内容为空”必须被视为同步失败，而不是同步成功。**

核心原则：

```text
路径正确 ≠ 文件正确
文件存在 ≠ 内容同步成功
GitHub Commit 成功 ≠ 数据同步成功
```

空文件检测只是最后一道保险，必须继续定位为什么源内容没有进入 Blob/Tree，或者为什么 Pull 后没有正确写入本地。
